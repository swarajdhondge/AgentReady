# Goal-directed execution

Translate the user's request into an observable outcome, acceptance checks, boundaries, and stopping conditions. Small work needs only a short statement; complex work benefits from a restartable living plan linked to discoveries and decisions. Reuse the project's existing plan format. There is no mandatory PLANS.md file or upfront specification of every implementation step.

Proceed through useful milestones: inspect evidence, implement within scope, verify the affected behavior, and record progress. Revise steps when evidence changes; explain consequential changes. Do not ask for approval of each routine step already authorized. Ask when a required product choice or change to accepted constraints lacks authorization. Continue independent work if possible.

When the user explicitly requests a persistent goal and native goal tools are available, use them with a verifiable stopping condition. Otherwise work within the current task and leave a checkpoint; do not claim a background loop will continue after the session ends. Scheduling, deployment, and paid activity need their own applicable authorization.

## Parallel work

Use supported native subagents for bounded independent work when delegation is authorized and provides value. Keep the user's selected main model in charge. Honor configured role/model preferences; if a requested model or feature is unavailable, report that rather than silently substituting. Do not mandate model brands, agent counts, reviews, or test-writing for every edit.

Give each worker the outcome, relevant discovery and decision sources, constraints including credential/spend restrictions, owned files or area, dependencies, and expected evidence. Workers must read their relevant sources, not merely the plan. Separate overlapping writes or serialize them. The main agent reconciles changes and new discoveries, resolves conflicts, and verifies the integrated result. More agents can consume more tokens; parallelism is not a cost-saving guarantee.

## Verification and stopping

Use existing checks proportionate to the changed behavior and repository requirements. Inspect commands before execution for external services, credentials, writes, or charges; use offline fixtures when live use is not authorized. Do not change tests merely to make failures pass or add tests for every reversible documentation/configuration edit.

Finish when the agreed outcome is demonstrated. If checks fail, investigate and repair within scope; record unrelated failures separately. Stop repeated attempts that yield no new evidence and report the blocker. A goal is blocked, rather than complete, when necessary evidence, authorization, or user decisions remain missing.

A handoff states the goal, settled constraints, changed files, checks and outcomes, discoveries, unresolved issues, and next useful action. Update the project's existing record, preserving uncommitted work and other contributors' changes.
